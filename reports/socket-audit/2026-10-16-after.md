# Socket.IO audit — after checks (2026-10-16)

## Conclusion

The production endpoint is reachable over HTTP polling and WSS. A Socket.IO Engine.IO session opens and the WebSocket upgrade succeeds. The namespace then rejects a no-credential connect with `SOCKET_AUTH_REQUIRED`. The current remote backend contract requires a kiosk ticket (`handshake.auth.kioskTicket`) or an employee JWT; a legacy connection that only passes `branchId` is no longer sufficient.

This is the confirmed backend-side failure mode. It is the likely cause if the affected kiosk still uses the legacy branch-query connection. The actual kiosk payload could not be checked because the client repository was explicitly out of scope and production PM2/Nginx logs were inaccessible. Therefore the exact client-side correlation remains unverified.

The required compatible kiosk flow is: obtain a short-lived ticket from `/api/kiosk/socket-ticket`, connect with `auth: { kioskTicket }`, obtain a fresh ticket when reconnecting after expiry, and refetch the queue after reconnect. The current ticket lifetime is 15 minutes. This client change is intentionally not made in the backend-only scope.

## Backend and event review

- Socket.IO is attached to the same HTTP server that serves Express.
- Production Engine.IO polling and WSS upgrade both respond successfully; this audit did not find evidence of a TLS/reverse-proxy upgrade failure.
- Authenticated kiosk tickets automatically join `branch:<branch_id>`; employee branch subscriptions are checked server-side. The unauthenticated legacy `branchId` query is rejected.
- Queue lifecycle handlers emit `queue:update` to branch rooms after successful database writes. Existing documentation correctly describes Socket.IO events as transient invalidation signals and requires a refetch after reconnect; no evidence here justifies a transactional outbox as the fix for this outage.
- A security finding remains: kiosk registration and ticket issuance routes are reachable without an authenticated device credential. Registration deletes the current kiosk record(s) for a branch before inserting a caller-selected device, and ticket issuance checks only `branch_id + device_name`. This permits a caller who knows/guesses those values to replace a kiosk registration and obtain a short-lived ticket. There is no backend-only way to make this identity proof strong while preserving a client that sends only those public fields. A device enrollment credential and client support are required before changing this safely.
