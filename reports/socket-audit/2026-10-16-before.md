## Initial findings

1. **Confirmed production behavior:** transport handshake is reachable, but an unauthenticated Socket.IO namespace handshake is rejected. HTTP health and Engine.IO 200 do not prove authenticated client delivery.
2. **Likely compatibility break (client behavior unverified):** the historical backend accepted legacy `handshake.query.branchId`; `origin/main` now ignores that for auth and requires `handshake.auth.kioskTicket` (kiosk) or JWT (employee). An unchanged kiosk that only sends the old branch query will receive `SOCKET_AUTH_REQUIRED`. The client repo was explicitly out of scope and was not inspected. Production logs were inaccessible, so the real kiosk handshake payload is not known.
3. **Security finding from static review:** kiosk registration and ticket issuance are unauthenticated. Registration replaces the registered kiosk row for a branch; ticket issuance only checks `branch_id + device_name` and then mints a 15-minute branch-bound ticket. This lets an unauthenticated caller who can supply/guess those values take over a kiosk registration and obtain that branch's live socket room. This must be fixed without exposing a public queue-room join.
4. **No durable-delivery evidence:** README documents `queue:update` as an invalidation signal and asks clients to refetch after reconnect; Socket.IO itself is not durable. Current scope does not establish a DB commit/event-loss incident.

## Change and test state

- Root cause is narrowed to the production auth contract and likely kiosk/client mismatch, but cannot be conclusively tied to a real kiosk without its handshake error/log or client behavior.

This rules out the TLS/WebSocket upgrade path as the failure in this probe.
